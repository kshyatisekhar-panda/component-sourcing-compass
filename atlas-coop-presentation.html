06 · Baseline Assumptions

What we're assuming
to be true going in

If any of these turn out to be different in reality, we'll need to revisit scope.

🗄️

Data is accessible

BOM repository, PO history, and supplier data can be queried programmatically — via DB, ERP export, or structured file.

🔑

Part numbers are consistent enough to match

MPNs are present in enough records to allow cross-product matching — with normalisation on our side.

📡

Mouser API access is available

We have or can obtain a Mouser API key. Free to access, returns live pricing and availability at component level.

✅

Compliance data exists in queryable form

RoHS and REACH status is recorded somewhere — supplier DB, certification register, or datasheets.

👤

PMs will use plain-language queries

The interface is conversational via Cline. No form-based UI — the AI interprets intent and fetches accordingly.

📊

Annual purchase volumes are derivable

Needed for savings estimates. Assumed to be calculable from PO history.

⚠️

Biggest risk: Part number inconsistency across BOMs. Different teams may have recorded the same component differently. We're budgeting time to build a normalisation layer — but if data is severely fragmented, cross-product matching will be limited for the demo.

Why the SVHC list lives in svhc-cache.json rather than being fetched on each call

ECHA publishes the SVHC list as XML or Excel on their candidate list page — not as a JSON API. For the demo, a snapshot is faster, more reliable on stage, and easy to verify against the public source. The file's top-level source and snapshot_date fields make provenance explicit in every tool response.

When compliance_check returns a violation, the response includes the same svhc_source_snapshot so consumers can audit where the rule came from. In production, the cache would be refreshed on a schedule — for example weekly — by a small fetcher that pulls the official list and re-emits it in the same format.
